# 1.1.5 后续：头像分区与附件实时归属

## 根因与证据范围

- 原头像选择器调用聊天附件保存函数，把用户及助手头像写入upload并登记为普通附件；文件归属只查聊天，当前头像因此落入“未关联助手”。
- ChatService接受发送时先把消息放进内存inbox，派发时进入submitting，之后才写message_node。只观察数据库会漏掉尚在排队或提交中的图片。
- 超262144字符的节点原来只标记未知；新扫描按SQLite codepoint分块读取并跳过长文本，仍能提取后面的真实附件。
- 以上通过生产序列化及队列/持久化路径复现；未读取用户实际聊天库，不把具体助手姓名硬编码进归属逻辑。

## 行为

- 文件页提供“聊天文件”和“头像”两个区域。当前旧upload头像在迁移完成前也按真实个人/助手设置独立显示，不虚构聊天归属。
- 新头像写入avatars目录；旧头像先复制、持久化更新真实引用，再考虑清理原文件。共享头像、背景、预设、收藏、历史消息及运行时队列/草稿仍引用的文件保留。
- 旧头像被替换后自动清理；取消或被更新选择覆盖的选图结果释放pending，启动时可回收保留目录中的无引用结果。未知的历史upload文件不凭文件名或尺寸猜作头像删除。
- 配置引用检查使用生产序列化器流式遍历，避免构造整份设置JSON副本，并保护编码的文件名及嵌套文本/键引用。
- 会话内存、inbox及submitting的变化实时参与归属。完整运行时历史覆盖同会话的旧数据库归属，移动助手不会误显示共享；未发送草稿只保护删除，不算已发送。
- 生命周期内显式订阅运行时引用，不使用跨服务或跨测试的全局可变注册表。未知/截断引用继续保护，默认未关联清理还会复核当前引用。
- 头像与背景编辑传入实际渲染快照，迁移期间编辑其他字段不会复活已经替换的旧图片。
- 备份读取设置后立即对核心资产创建私有磁盘快照，两种导出都写入快照并去重；缺失、复制期间改变或取消会使备份失败，而非成功产出缺图包。恢复及网页文件访问支持avatars目录。
