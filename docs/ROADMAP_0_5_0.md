# Rikkahub-M v0.5.0｜激进式实质重构与上游追赶计划

> 2026-11-22 制订。**这是下一版本任务书，不代表已实现。** 基线 RM `4a5896a`（0.4.5 源码），RB `2435dbd`（3.3.1）；开发开工必须先拉最新 master 并复核 [差异主文](RM_VS_RB.md) 及 [235 文件路径清单](RM_VS_RB_FILE_DIFF.md)。正式版本目标 **0.5.0 / versionCode > 20**，保留 `com.rikkahub.mate`、原正式签名、一个 universal APK。
>
> 工作方式：大胆修改内部架构、强制清理冗余、主动合入上游改进，拒绝只出建议/空文档。**但对隐私、存量用户数据、签名、许可、发布质量采取严格保护**；未验证不得谎称通过或绕过 CI。

## 目标产品

使 RM 相比 RB **保持原生功能，不因 fork 丢失优秀上游能力**，同时成为更简洁、更流畅、独立维护、无推广、更可靠的移动端 AI 客户端。

**此次优先级：P0 可更新、可恢复、可升级；P1 性能/消息/记忆；P2 视觉/文案；常态维护上游差异文档。**

## 阶段 0：先全面对比，禁止先拍脑袋重写

1. 检出 RB 与 RM 的最新 master，固定 commit SHA，使用 git diff、文件树、依赖/资源差异、构建脚本及 UI 导航树生成可重复的差异报告。
2. 以 [235 路径冻结快照](RM_VS_RB_FILE_DIFF.md) 为起点，检查每个差异路径的业务含义。分类成 RM 增强、RB 新功能、冲突、重构、遗留废代码、文档和测试；**不得把相同文件认作无功能差异，也不得用文件名直接断言功能可用。**
3. 对 RB 未合入的 10 个 commit 单独审查：重点上游 `2d93676e` 安全模式备份、`fbfb9926` Google 模型、`b7cf74dd` Phone Use、`48a68f87` 模型列表、`e4646a77` 导出时间戳、`358e2931` bettertext；版本号、上游发布工作流、赞助资料不能覆盖 RM。
4. 将差异表附来源路径、对应 SHA、处理决定、验收结果；合并新版本时更新 README 差异链接。

## P0：更新发布与数据安全，必须先打通

- 先检查当前 v0.4.5 是否已有真实 Release APK/正式构建，并定位授权/系统安装器状态机；在 Android 8–17、至少一个国产 ROM 可模拟的权限路径上验证无权限→跳转→返回→继续安装；失败可回滚到浏览器下载，绝不静默安装。
- 整理 GitHub API→Atom→国内 HTTPS 更新源→缓存的退化策略，限定镜像可信来源，检查 TLS、SHA-256、包名、签名、versionCode、下载完整性与重复点击；避免 403/404 后死循环。任何镜像更新只能在确认证书和固定签名后接受。
- 备份 UI 进一步收敛成日常“立即备份/恢复/自动备份”，高级配置折叠但保留 WebDAV/S3；新备份免口令且加密，旧口令归档可恢复，不能删除用户原有 ZIP。给恢复密钥导出/导入、丢失提示、不同设备恢复、密钥不可用、文件损坏、空间不足做单测和模拟器回归。
- 上游安全模式完整备份能力与 RM 0.4.4 加密机制合并成一个正确实现：即使 Room schema 迁移失败，仍能只读备份原有 DB/WAL/SHM、附件和设置，并在恢复前校验版本、签名/清单/完整性，避免覆盖当前健康数据。
- 明确保留旧数据迁移路径：从 0.2.4、0.3.x、0.4.2、0.4.4/0.4.5 的存量 APK 或测试 fixture 做覆盖升级，签名证书与历史相同，数据库/助手/聊天/头像/提示词/记忆/附件保留；切忌删除或清空个人数据以“通过测试”。
- GitHub Actions 真正执行 release 构建、JVM/仪器测试、Lint、单一 universal APK、签名 SHA-256、包名、ABI、版本码、备份与升级数据契约；失败不能发布稳定版。发布不是写文档假装发布。

## P1：全面性能整治（不准删动画充数）

- 用 Macrobenchmark/Trace/Compose 重组统计和实际可核实的测试设备，找冷启动、聊天长列表、消息富文本、流式重组、输入法动画、导航切换、图片缓存/附件解码等 CPU/主线程热点。
- 分别构造 500/5,000/20,000 条消息、超长 Markdown/代码/Mermaid、多张图片、流式高频刷新；保留 Material 3 Expressive 的连续微动效与手势，减少多余重组、重复 Markdown 解析、过量状态收集与不必要的 I/O。
- 对真实设备采集首帧、完全可交互耗时、帧时间 p95/p99、Jank、Peak PSS、消息滚动与耗电趋势；在 `docs/perf/baseline.json` 标注设备、构建、采集方法及采样日志。**没有实机就写“未测”，不得编造提升百分比。**
- 修复聊天分页、滚到底部/加载历史的稳定性、流式丢块/重复/中断/取消、附件与输入框响应。为每一个已复现 BUG 写最小回归测试。

## P1：助手/提示词/长期记忆工程化

- 保留本地多助手、独立名称/头像/提示词；默认助手不能被第二套隐藏聊天逻辑覆盖，禁止自动切到旧云网关。
- .md/.txt/.json 导入需要真正可编辑的规则名、启用状态、优先级、注入位置、助手绑定；验证新建聊天、换模型、重启、备份恢复后确实生效。只在用户指定助手的配置中展示个人自定义名称，不把私人人格写死进公共代码或文案。
- 统一长期记忆的数据模型与 CRUD：列表/搜索/编辑/删除/最近删除/恢复/手动保存当前消息、自动提炼开关与审计；校验用户可控、去重、正确召回和会话隔离。成长人格独立文件与版本回滚属于可选后续方向，不得未经用户授权更改真实人格或历史记忆。
- 补全 provider 余额计算、NewAPI 响应容错、峰谷状态仅在来源确实可用时显示；不存在可验证 API 时不造假余额。

## P2：全局视觉/文案/冗余清理

- 在 RM 原有 Compose 层上连续优化，不另做一套割裂的 UI；统一排版、密度、字号、圆角、图标/动画、深浅色、无障碍与平板适配；聊天、模型选择、设置、关于、更新日志、记忆、备份、选择文件等必须统一。
- 默认简体中文，保留英文及既有多语言；“设置/帮助/关于”短文案，不出现旧 Mate 网关等废弃入口；删除重复 Toast/异常弹框，但保留诊断能力。
- 保持官方 RikkaHub 的合法版权与 AGPL 义务；不恢复赞助/捐赠/广告推荐、不植入推荐站、不把非官方 fork 伪装成原项目发行。
- 移除真正不可达的旧代码、重复数据路径、过时资源、废弃依赖，但先跑引用与迁移搜索，绝不能因为名字带 Mate 就删除实际正在使用的备份/更新组件。

## 执行方式：高强度自主交付，不要反复空谈

1. **实际代码修改**：合理分 4–8 个可审阅 PR/commit（上游移植、更新/备份、安全模式、性能聊天、记忆提示词、UI 文案、测试发布），每块独立能编译。
2. **自主修到 CI 通过**：读取 Action 失败日志、复现问题、补测试再重跑；禁止跳过关键测试或弱化门禁。
3. **隐私边界**：不要读取、收集、打印、提交私人人格、聊天、API Key、数据库、密钥、恢复文件、云服务器凭据；仅使用合成 fixture。无真机/生产权限时推进剩余工作并标明边界，不以此为理由停止全部开发。
4. **变更账本**：每个任务附 before/after、具体文件、commit SHA、对应测试、是否真机验证与风险。未完成项单独列出，绝不冒充成功。
5. **发布**：0.5.0 只在所有可自动化的必需 P0 测试成功、签名/升级验证通过后发布；真机尚未覆盖的路径必须在 Release 明确标注，若触及高风险数据迁移且缺真机测试，先出候选版，不能标稳定。
6. **验收报告**：提供最终主分支 SHA、PR 链接、Actions run ID、APK 名称/大小/SHA-256、签名指纹、versionName/versionCode、已通过/未通过清单、下一轮优先项；没有产物明确说没有。
