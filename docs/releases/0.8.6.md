# Rikkahub-M 0.8.6

发布策略：0.8.6 是一次结构修复版本。记忆从「助手详情的三级页面」提升为一级功能；更新下载的主线程异常找到并修掉真正的根因；记忆整理失败从「一句话报错」变成可解释、可恢复、不重复计费。只新增失败诊断列，不动用户数据。

## 一、信息架构：记忆提升为一级功能

- 新增 `Screen.MemoryCenter`（RouteActivity.kt）与 `ui/pages/memory/MemoryCenterPage.kt`、`MemoryCenterVM.kt`。
- 侧边栏入口原来是 `if (memoryDreaming) MemoryDreamingEntry(...)`：关闭自动整理后入口整体消失。现在改为常驻 `DrawerEntry`，整理中只在行尾显示一个 16dp 进度点；设置主页也新增「记忆」入口。
- 记忆中心首页：记忆库 FilterChip（助手名 / 所有助手共享）→ 统计条（记忆文件 / 待确认 / 已跳过）→ 最近整理状态行（运行中可暂停/结束，失败可重试，暂停可继续）→ 常用动作平铺（智能整理、从历史提取、确认记忆、已跳过、任务历史、使用记录）→ 搜索 → 可折叠分组列表 → 最近删除。右上都只剩「记忆设置」，日常功能不再藏在 ⋮ 里。
- 作用域：`MemoryCenterVM` 只有一个 `scope: StateFlow<String>`，由 `assistant.memoryId`（即 `useGlobalMemory`）推出默认值；显式切换才写偏好。标题、列表、搜索预览、job 观测、候选计数、使用记录、任务历史全部由它 `flatMapLatest` 派生，切库不会出现「标题换了、列表没换」。默认不开启全局共享。
- 自动保存只认启动本轮任务时的那个 scope（`autoJob = (scope, jobId)`），用户中途切库也不会把候选写进另一个记忆库。
- `AssistantMemoryPage` 从 998 行收敛到 120 行：只剩「打开记忆中心」+ `MemorySettingsScreen`（启用记忆、全局共享开关、自动整理、预算、模型、时间提醒）。

## 二、P0：更新下载 NetworkOnMainThreadException

- 根因：`UpdateChecker.httpGet` 使用 `Call.await()`。`await()` 只把 enqueue 交给 OkHttp 调度器，协程恢复后回到**调用方**的调度器，紧接着的 `response.body.string()` 就在那个线程上真正读 socket；调用方是 Main 时就抛 `NetworkOnMainThreadException`。改为 `withContext(Dispatchers.IO)` 内 `execute()` 并读完正文。
- `startDownload` 重构：主线程只做「置状态 + `startForegroundService`（Android 12+ 限制要求点击时刻在主线程）」，把构造 sources、下载、APK 校验、记住可用源整段交给 `downloadInBackground()`；结果由 `publishDownloadOutcome()` 回到主线程发布。`init` 的清理与半截文件统计、`bundledNotes()`（assets）、SharedPreferences 读写全部移出主线程。
- 引擎新增 `UpdateStage`（PREPARE/CONNECT/TRANSFER/VERIFY/VERIFY_ARCHIVE），失败状态追加「失败阶段」，并 `Log.w` 记录阶段 + 版本 + 异常类名；`describeDownloadError` 对 ONM 单独提示「内部错误，请反馈版本号与日志」，不再伪装成网络问题。
- 修复客户端缓存 bug：`downloadClient` 原来只缓存第一个 base client，之后换设置（代理/拦截器/超时）都会继续用旧实例；改为按 base client 的 `WeakHashMap` 缓存。

### 证明手段（四层，互不重复）
1. `UpdateMainThreadTest`：`Dispatchers.setMain(StandardTestDispatcher())` 后从 Main 发起下载，用 OkHttp `addNetworkInterceptor` 记录真正执行 socket IO 的线程，断言非主线程；覆盖整包下载、Range/206 续传、切源 + 500 退避重试、阶段序列。
2. `UpdateMainThreadSourceGuardTest`：源码级守卫。抹掉注释与字符串后粗解析函数体，凡含 `newCall(/.execute()/body.string()/readText/writeText/inputStream/FileOutputStream/listFiles/getPackageArchiveInfo/assets.open` 的函数必须自己包 IO 或在「只由 IO 段触达」清单中；禁止 `await()` 与 `runBlocking`。这条是防回归的关键——注释挡不住回归，扫描能。
3. `UpdateMainThreadInstrumentedTest`：真机 StrictMode（线程级策略，必须在主线程设置）+ 对照用例（主线程直接开 socket 必须被抓到），否则「无违规」不算证据。
4. `scripts/verify_apk_artifact.py`：发布产物门禁，校验 dex 里存在本版 versionName / versionCode 与版本独有标记。用户那次截图最可能的原因就是「装上的不是含修复的产物」，这条门禁专门卡它。

## 三、P0：记忆整理失败可诊断、可恢复

- 新增 `MemoryFailure.kt`：`MemoryStage`（reading_history / model_config / prompt_build / model_call / response_parse / db_write / worker_schedule / unknown）、`MemoryFailureCode`、异常分类（超时、401/403/429/413/5xx、解析、SQLite、IO）、`sanitizeFailureDetail`（去掉 sk-*、Bearer、api_key/token/secret、URL 查询串）、用户文案与建议的唯一来源。
- `HistoryMemoryManager`：主循环每步显式 stage；`fail()` 不再只在 `status == "running"` 时落库——暂停、取消、换代时失败原因也会写进 `history_memory_task_log`（这是「什么都没发生」的主因）。
- 批次级失败：模型调用成功但解析/写库失败时，以前 digest 不记账、游标不动，点一次「继续」就重新调一次同一批。现在 `batchAttempts` 连续失败到 3 次自动 markProcessed + markSeen + skippedBatches+1 后继续，成功则归零；成本有上限，任务不会卡死。
- 终态型错误（来源会话被改/删、消息 JSON 损坏）改为按会话跳过并记 `skippedSources`，其余会话继续整理。
- 僵尸任务：`refreshTaskLogs` 会先 `releaseStaleLock`，把「数据库说 running 但 WorkManager 没有活」的任务标为 paused 并说明原因；enqueue 失败也会落成 `worker_schedule` 阶段失败。
- 任务历史页显示「在『阶段』失败：原因 + 建议 + 自动跳过 N 个批次/会话」，新增「复制诊断」（剪贴板，不含正文与密钥），重试按钮改为「从这一批继续」。

## 迁移与数据安全

- Room 40→41：`Migration_40_41` 只有 9 条 `ALTER TABLE ... ADD COLUMN`（job：failureStage/failureCode/failureDetail/batchAttempts；task_log：errorStage/errorCode/errorDetail/skippedBatches/skippedSources），不建表、不删表、不重建、不动索引。
- 新增列为 NULL 时任务历史自动回退到原来的单行原因，不会显示错误的阶段。
- 记忆文件、候选、批次指纹、scope 状态与聊天数据不受影响；`MemoryFailureColumnsMigrationTest` 校验老数据原样、新列可写。
