# Rikkahub-M 0.8.5

发布策略：0.8.5 补上 0.8.4 明确欠账的「记忆任务历史」，并按审计结果修掉列表动效、二级页转场、自建主题系统栏三处不一致。只新增一张表和少量界面改动，不改包名、签名与已有数据结构。

## 记忆任务历史（P0/P1 五）

- 根因：`history_memory_job` 主键是 scope，每个记忆库只保留“当前这一轮”，任务被新任务替换后上一轮的信息就查不到了；用户只能看到界面上的三个数字，无法回答“上次整理了哪些会话、花了多少 Token、为什么失败”。
- 新增 `history_memory_task_log`：id=任务 id、scope、generation、createdAt/finishedAt/status、sourceCount、processedCount、candidateCount、savedCount、skippedCount、inputTokens/outputTokens、rangeLabel、errorMessage。
- 写入口径：进度来自任务游标 `sourceIndex`；候选/已保存/已跳过直接对 `history_memory_candidate` 做 COUNT；Token 优先取 provider usage，缺省按字符数估算，与 `estimatedTokens` 同口径，并按批次累加而不是覆盖。
- 任务行与历史行通过 `saveJob()` 一起写，避免历史显示“仍在整理”而任务其实已经停下；每 scope 只留最近 100 轮。
- 打开历史页时 `refreshTaskCounts` 对齐一次计数，用户事后审核候选不会让历史数字停在任务结束那一刻。
- 重试只对“当前仍然是这一轮”的 failed/paused/interrupted 生效；被替换的旧轮次只回看，不假装能续跑。
- UI：记忆页「⋮ → 任务历史」，列表给出时间、范围、候选数与 Token，失败原因直接显示；详情可看进度与保存/跳过分布，可打开本轮待确认候选。

## 迁移（P1 八）

- Room 39→40：`Migration_39_40` 只 `CREATE TABLE IF NOT EXISTS` + 建索引，不重建、不删除任何已有表。
- `app/schemas/.../40.json` 与迁移 SQL 的 createSql/索引已逐字比对一致；androidTest 里新增 `MemoryTaskLogMigrationTest`，断言 39 库里的记忆状态、任务行原样保留、新表默认值正确、索引存在。
- 升级前已经跑完的轮次没有历史记录：当时没有采集，不做任何伪造或回填。

## 列表动效与转场（P1 六/七）

- 9 处 `items(...)` 补稳定 key（文件夹、文件夹 chip、搜索结果、MCP 工具、备份文件等），其中会增删的文件夹列表与 chip 行加 `animateItem()`；会话列表补 `contentType`，三种行结构不再共用组合。
- 刻意不加动画：聊天消息列表（流式输出时逐帧改高度会导致整列抖动）、纯字符串建议列表（无 id，加 key 会崩）、未去重的远程模型列表（重复 id 会让 key 冲突）。
- 删掉 `entry<Screen.Chat>` 的淡入淡出覆盖：root 层淡入已由 `backStack.size == 1` 分支负责，而该覆盖漏了 `predictivePopTransitionSpec`，导致手势返回与按钮返回不同源。MediaCreation 的容器变换属于受支持的例外，保留并注明理由。
- 系统栏图标改为按 `colorScheme.background.luminance()` 判断，而不是跟着深色模式开关：自建主题允许深色模式配浅色底。
- 模型选择弹窗的 `filterByKeywords` 与已选计数改为 `remember` + `HashSet`，去掉每次重组都全量过滤与 O(n·m) 比较。
- 两处页面级裸 `CircularProgressIndicator` 统一为 `LoadingIndicator()`；行内图标槽位（24dp）与文件页纯文字报错按“不新造语义”保留。
