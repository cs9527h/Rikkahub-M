# Rikkahub-M 0.8.4

发布策略：0.8.4 修复两个 P0 故障（应用内更新下载主线程崩溃、历史整理僵尸任务锁）与 Token 估算虚高。只改代码与估算，不新增数据库迁移。

## 更新下载

- 根因：`AppScope` 是 `Dispatchers.Main`，`UpdateDownloadEngine.download` 在调用方线程直接执行 OkHttp `execute()`、文件写入与 SHA-256，真机抛 `NetworkOnMainThreadException`，两个来源都以同一原因失败。
- 修复：`download` 整体包进 `withContext(Dispatchers.IO)`；`UpdateInstaller.downloadAndVerify`（包名/签名校验也走 PackageManager）同样切到 IO。
- 回归测试：断言实际 HTTP 请求发生在非调用方线程。
- 未使用 StrictMode 豁免，也未关闭任何 TLS/签名校验。

## 历史整理任务

- 根因：`persistConfirmedPlan` 只允许在 `finished`/`cancelled` 之后新建任务；进程被杀或 WorkManager 被系统清理后，数据库里的 `running` 永远不会结束，用户只看到「已有任务正在运行或等待处理」。
- 修复：新增 `HistoryMemoryWorker.isActive`，用 WorkManager 的真实任务状态判断；`releaseStaleLock` 与 `resumePending` 会把“数据库 running 但无 worker”的僵尸任务标记为 paused 并说明原因。
- 新建整理允许在 `finished` / `cancelled` / `failed` / `paused` / `interrupted` 之后进行；旧候选仍按 scope 保留，不会被删除。
- 回归测试：在 instrumented 用例中把任务行置为 `running`（无对应 WorkManager 任务），验证仍能新建任务且 201 条候选数量不变。

## Token 估算

- 旧公式用 `nodes / 12` 当请求数，把助手回复、附件与空节点也算进去，291 个会话被估成数百万输出 Token。
- 新公式：请求数 = max(会话数, 字符数/8000+1)；输入 = 字符/2 + 请求数×240；输出上限 = min(请求数×512, 字符/12 + 请求数×40)。
- 文案明确「已完成批次会自动跳过，实际发送通常更少」。

## 兼容

- 无 Room 迁移，数据库版本保持 39。
- 包名、签名、记忆、候选、聊天与人格配置不变。
