## 每月自动审查的使用与失败处理

- 入口：[月度工作流](<../.github/workflows/upstream-review.yml>)；每月1日UTC01:00（中国09:00）及`workflow_dispatch`，只从仓库默认分支执行。并发任务串行，不取消正在进行的审查。
- [机器状态](<upstream-sync-state.json>)中的`reviewed_upstream`固定为本轮已审SHA；脚本的计划、clean-pick或PR合并均**不自动推进已审基线**。处理完所有manual/conflict/blocked项后，由人工另行更新基线并说明保留差异，避免跳过尚未评估的功能。
- 上游URL在[独立脚本](<../scripts/upstream_review.py>)内固定为`https://github.com/rikkahub/rikkahub.git`，每次fetch后固定`FETCH_HEAD`完整SHA。历史被重写、不含已审基线时停止，不猜测新共同祖先。
- 只新建`sync/upstream-YYYY-MM`。本地或远端同名分支已存在时停止并上传错误；推送还带“远端原OID必须为空”的原子lease，既不追加也不覆盖已有月分支。重跑时先检查已有PR，不自动删除/重置分支；需要重新审查时由维护者明确处理，或等下一月。
- 自动候选必须为非breaking Conventional Commit `fix:`/`fix(scope):`，且仅触及白名单模块源码文本。feature、merge/root、binary、symlink/gitlink/可执行位、异常路径、CI/构建/依赖/版本/发布、脚本，以及本地数据/会话服务/workspace不变量均转manual；跟随较早manual项修改同一路径的fix也转manual。
- clean-pick仅表示补丁可干净应用，**不表示已验证语义或编译通过**。bot不执行上游任何构建/测试/脚本，不自动批准/合并/发布。上游标题、路径、正文全部通过argv和转义报告处理，不插入shell命令。
- 每次应用前确认分支和干净工作树；冲突立即`cherry-pick --abort`并停止后续候选，后续项记blocked。保留先前成功项和错误证据，生成需人工处理的草稿PR；该次任务仍以非零exit失败。abort失败时保留现场并停止，不强制reset。
- 新分支会记录[最新审查台账](<audit/upstream-review.md>)和state中的`last_review`，每项包含完整SHA、分类、应用状态、理由、变更路径；应用项另记本地SHA，冲突另有有界git证据。master不被脚本直接修改。
- 输出`review.md`、`review.json`、`status.json`在runner临时目录，并通过always步骤上传90天artifact与job summary；实际PR URL只在`gh pr create`成功并返回合法URL后记录。创建PR权限被禁时任务明确失败，分支可能已推送，此时可手动开PR或处理权限后再检查已有分支，不伪称成功。
- job只有`contents: write`与`pull-requests: write`；仓库另需允许Actions创建PR。使用GITHUB_TOKEN创建的分支/PR通常不再触发其它Actions：维护者必须显式运行已有完整测试/升级/发布门禁，不能把缺少自动检查当通过。
